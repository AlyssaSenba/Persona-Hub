# DECISIONS — 决策记录

> 记录“为什么这么做”，避免以后反复推翻。每条包含：决定、理由、替代方案、后果。
> 状态：`accepted`（已定）、`provisional`（暂定，可改）、`deferred`（以后再说）。

## D001 只给自己用，Windows + Linux

- 状态：accepted（已修订：原为“Windows 优先”）
- 决定：首版单用户；Windows 与 Linux 都要能运行；不做账号/云/商业化。
- 理由：最快落地；避免合规、分发、多端同步的复杂度。
- 替代：给朋友用/开源/商业化（暂不考虑）。
- 后果：安装包、隐私说明、内容分级可以后补；架构不为此过度设计。

## D002 React + TypeScript 前端；桌面壳待定

- 状态：accepted（已修订：原为“Electron + React + TypeScript”，壳的选择被 D047 撤回）
- 决定：前端用 React + TS；桌面壳（Tauri / 正式签名 Electron / 其他）在 P1 评估后再定；P0.5 是本地 Node 服务 + 浏览器。
- 理由：前端与壳解耦，壳的选择不阻塞人设调试。
- 替代：直接定 Electron 或 Tauri（D047 的启动崩溃说明需要先验证）。
- 后果：托盘 / 自启 / 系统通知等能力要等壳确定后实现，且需分别适配 Windows 与 Linux。

## D003 单伙伴，数据结构预留多角色

- 状态：accepted
- 决定：v1 只有一个 AI 伙伴；数据库/文件结构预留 `persona_id`。
- 理由：符合“一个 AI、多个房间”的立意；避免人格分裂。
- 替代：多角色共享/独立记忆（复杂，暂不做）。
- 后果：以后加角色不需要重做数据层，但 UI 仍以单角色为主。

## D004 纯文字 + 氛围背景，不做立绘/语音/桌宠

- 状态：accepted
- 决定：文本为主；暖色房间/夜灯/纸质背景，随时间变化；不做角色立绘、Live2D、3D、TTS/STT、桌宠。
- 理由：降低美术/授权/性能/工程复杂度；先把内容和记忆做好。
- 替代：2D 立绘/Live2D/VRM/语音（P3）。
- 后果：沉浸感靠文案、时间、背景、打字状态、UI 音效（默认关）来补；预留升级位。

## D007 记忆自动写入 + 收件箱

## D008 记忆范围：咨询敏感，其他互通

- 状态：accepted

## D009 上下文分层 + 压缩 + 检索

- 状态：accepted
- 决定：每轮 8–12k 高信号内容；旧对话压缩归档；按需检索；不塞满 1M。
- 理由：Chroma 的 context rot 证明长上下文会降智；成本也会上升。
- 替代：全量 1M（短期简单，长期差）。
- 后果：需要摘要/检索/评测；回答可能“没找到记忆”，但不会假装记得。

## D010 模型：DeepSeek Flash，聊天默认不深度思考

- 状态：accepted
- 决定：`deepseek-flash`；所有聊天默认 `thinking: disabled`；用户可手动开 high；背景任务/复杂规划可单独用更高档位；后台批处理用便宜调用。
- 理由：用户要求聊天不要默认深度思考；低延迟/低成本。
- 替代：默认 low/high（慢/贵）；全 high（不可取）。
- 后果：聊天输入框提供开关；high 显示更慢/更贵提示；成本面板。

## D011 思考 + 工具：工具回合关思考

- 状态：accepted（实现细节可能调整）
- 决定：带 `tools` 的请求默认 `thinking: disabled`；聊天 high 仅用户手动开，且默认不挂工具；需要“high + 工具”时两阶段或自定义适配器。
- 理由：DeepSeek 要求带 tools 时回传 `reasoning_content`，否则 400；AI SDK 生态支持不完整。
- 替代：自定义适配器完整保存/回传 reasoning_content（更复杂，后续可做）。
- 后果：聊天 high 通常只用于无工具回答；需要工具时自动降级或分两段。

## D012 数据放工作区，私密内容不进 Git

- 状态：accepted
- 决定：`data/`、`memory/`、`config/`、`backups/` 在工作区；`.gitignore` 排除；API Key 加密。
- 理由：用户要求所有新建文件尽量在工作区；可见/好备份。
- 替代：AppData/Documents/云同步。
- 后果：工作区移动=数据移动；Git 仓库不含隐私。

## D013 API Key 用系统凭据加密

- 状态：accepted
- 决定：P0.5 只存 Node 进程内存，不落盘；需要持久化时（P1+）用系统凭据库（Windows 凭据管理器 / Linux libsecret），无可用凭据库则回退为仅内存；前端只见“已配置”。
- 理由：不把 Key 放明文/日志/Git。
- 替代：明文配置文件（不安全）。
- 后果：P0.5 每次重启服务要重填；换系统用户 / 重装后持久化的 Key 可能需重填。

- 理由：防止“玩游戏玩到人设崩”，也避免“每句都一个腔调”的死板。
- 替代：完全角色扮演（容易 OOC/越界）；完全不准扮演（少乐趣）。
- 后果：Prompt 分层；游戏事件单独标记；固定评测集。

## D043 人设调试模式：安全词/快捷键 + patch + 预览/回滚

- 状态：accepted
- 决定：安全词（本地拦截）、快捷键/特殊 key、设置页三种入口；输入自然语言 → 结构化 patch → 预览 3–5 轮 → 应用/回滚；patch 只改表达层，不改安全/内容/危机/能力边界。
- 理由：用户需要“哪句话不对就立刻调”，且不能因此把人设改崩或绕过安全。
- 替代：直接改系统提示（危险/不可回滚）；只能改配置文件（门槛高/要重启）。
- 后果：需要 patch schema/白名单/版本/预览/审计；调试模式是隐藏模式，不是后门。

## D044 AI 的情绪表达权 + 反表演

- 状态：accepted
- 决定：AI 可以表达由用户触发的情绪（开心/难受/吃醋/生气/失落），但要有原因、适度、不操控、不声称生理感受；不默认“回应+反问”，不套人类恋爱话术，不为了像人加戏。
- 理由：用户要“有情绪”，但不要“演/模仿人类的虚假感”。
- 替代：完全无情绪（面瘫）；过度戏剧化（假）。
- 后果：需要情绪/反表演规则、示例、评测；情侣冲突有专门边界。
